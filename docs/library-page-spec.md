# 曲目库页规格（用户 2026-09-25 确认口径）

这份是**曲目库页的唯一口径**。用户原话要点 → 已确认的落地方式，两边（前端 Trae / 后端 ZCode）
都按这份做，有分歧先改这份再写码。

## 0. 分期

- **一期（进行中，Trae）**：只读版——选文件夹扫描入库、列表 + 筛选（搜索/BPM/调性/genre）、
  详情抽屉（cue 只读）、统计与偏好看板。要求预留：**入库进度显示位**、**封面显示位**、
  **右键菜单骨架**（先只放"打开所在文件夹"这类只读动作）。
- **二期（本文其余部分）**：入库进度、封面提取、右键菜单全量、删除、重命名、归类、去重。

## 1. 入库 / 扫描

- 用户选文件夹（可整盘）→ `library.scan_folder`（已有：指纹增量 = size + mtime + 头尾 64KB 哈希；
  第二次扫同目录只读变化的文件）。
- 扫完自动接着 `library.analyze_missing` 补 BPM/调性（已有），**封面提取**（新增）也在这一步做。
- **进度**：任务表（SQLite `scan_jobs`：id/status/total/done/failed/started_at/finished_at）+
  **SSE 推送**给前端（不用轮询）。前端显示：`正在入库 423/10000 · 当前 artist - title.mp3`。
  每完成一首或每 500ms 推一次。
- 失败文件：跑完界面显示"12 个文件失败"，点开是清单（路径 + 原因：无法解码 / 检测超时 / 权限拒绝），
  可导出 txt。**不静默吞掉失败**。

## 2. 封面（新增）

- 优先顺序：**嵌入封面（ID3 APIC / FLAC picture / M4A covr）→ 同目录 `cover.jpg` / `folder.jpg`
  → 没有就占位图**。**不联网**拉封面（1 万首会拖到几小时）。
- 提取：用 `mutagen`（已够用，支持 MP3/FLAC/M4A/Vorbis）。
- 存储：写小图到 `_library/covers/<track_id>.jpg`，**DB 只存 `cover_path`**（不存 BLOB，
  否则 1 万首会让库涨到 GB 级）。
- 性能：封面提取是 I/O 活，用 `ThreadPoolExecutor(max_workers=4)` 并行；不会成为瓶颈
  （BPM 分析每首 1–3s 才是大头）。

## 3. 删除（**破坏性，按用户确认的口径**）

**两个动作分开，绝不合并**：

| 菜单项 | 行为 | 确认 |
| --- | --- | --- |
| **从曲库移除** | 只删 DB 行，**文件不动**（文件还在，下次扫描会重新入库 → 可逆） | 不需要 |
| **移到废纸篓** | `shell.trashItem(path)`（跨平台：macOS 废纸篓 / Windows 回收站）+ 删 DB 行 | **必须二次确认** |
| **彻底删除**（次要选项） | 直接删文件（`unlink`），不可恢复 | **更重的确认**：勾选"我知道无法恢复"才可点 |

二次确认弹窗文案（照抄）：

```
删除以下文件？
artist - title.mp3（8.4 MB · WAV 24bit/48kHz）
文件将移入系统废纸篓，曲库记录一并删除。
[取消]  [移入废纸篓]
```

**默认永远是废纸篓**；"彻底删除"只是给确实想删干净的人。

## 4. 重复歌曲（三层判定，只有一层拦人）

| 层 | 判据 | 处理 |
| --- | --- | --- |
| 一 | 文件内容哈希（sha256/头尾哈希） | **完全重复** → 自动标记 + 报告里列出，不弹窗 |
| 二 | **声学指纹**（Chromaprint / `fpcalc`） | **同一录音的不同编码（wav vs mp3 等）→ 弹窗让用户二选一** |
| 三 | 元数据（artist + title 标准化后相同） | 只打"疑似重复"角标，**不弹窗**（remix/edit 会误伤） |

"二选一"弹窗里要能看到（按重要性）：**格式 / 位深·采样率 / 大小 / 时长 / 完整路径 / 入库时间 /
BPM·调性是否一致**；按钮是"保留这条（另一条移入废纸篓）"，**永不自动删**。

- 依赖：Chromaprint（`fpcalc` 二进制，macOS 可 `brew install chromaprint`）。**没装时**：第二层降级为
  "只按哈希 + 元数据"，并在界面写明"未安装声学指纹，重复判定会保守"。

## 5. 右键菜单（最终形态）

```
打开所在文件夹      ← 只读
试听
编辑名称…          ← 改 DB 的 title（文件标签不动；要不要写回标签后面再议）
加入分类库 ▸        ← 二级菜单：已有 crate 列表 + 新建
从曲库移除          ← 只删 DB 行，文件不动
────────────
移到废纸篓…         ← 危险项，红色，二次确认
彻底删除…           ← 更危险，勾选式确认
```

## 6. 移动 / 分类

- **"归类" = 加入 crate（逻辑分类），不动文件**。一首歌可属于多个 crate；不影响 Rekordbox/Serato
  的路径引用。这是日常主操作。
- **真"移动文件"**：做成次要功能，弹窗警告"移动后 Rekordbox/Serato 中的引用将失效，需要重新链接"，
  并且提供"同时更新曲库路径（我们自己的 DB）"。**默认不提供批量移动**——建议用户入库前在
  Finder/资源管理器里整理好再扫。

## 7. 验收口径（谁做谁跑，Codex 复验）

1. 扫一个真实小目录（≤10 首）：进度事件 ≥2 条（能看到 total/done 递增）、入库后每首都有
   BPM/调性/时长、有封面的那首 `cover_path` 存在且能显示、失败清单为空。
2. 删除：对一首**副本**测"移到废纸篓"→ 文件从原目录消失、出现在系统废纸篓、DB 行没了；
   "从曲库移除"→ DB 行没了但**文件还在**（这是两条断言，别只测一条）。
3. 去重：造一对"同内容不同格式"（同一 wav 转 mp3）→ 第二层必须报出并弹窗；造一对
   "同名不同版本"（原版 + 改 3 个音的 edit）→ **不许**判成必须二选一，只能打"疑似"角标。
4. 归类：一首歌加入两个 crate → 两个 crate 都在、文件路径没变（`path` 字段逐字节相同）。
5. 全程零 console error；破坏性操作每一步都有确认，**没有"点了就直接删"的路径**。
